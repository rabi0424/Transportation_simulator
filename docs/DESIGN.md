# 新設路線シミュレーター 設計書

既存の公共交通ネットワーク(鉄道・バス)に対して新設路線計画を入力し、
**利用者数の予測**・**所要時間短縮効果**などを計算して地図上に可視化するツールの設計書。
対象地域は日本国内とする。

---

## 1. 目的とユースケース

### 1.1 目的

- 新設路線(鉄道新線・延伸・BRT 等)の計画案を地図上で手軽に作成できること
- 計画案の効果(利用者数・時短・アクセシビビリティ変化)を定量的に比較できること
- 複数のシナリオ(ルート案 A/B/C)を並べて評価できること

### 1.2 想定ユーザーとユースケース

| ユーザー | ユースケース |
|---|---|
| 交通計画の学習者・愛好家 | 「もしここに新線があったら」を試して効果を見る |
| 自治体・コンサルの初期検討 | 概略ルート比較のスクリーニング(詳細検討の前段) |
| 研究・教育 | 四段階推定法の簡易実装を使った演習 |

> **注意**: 本ツールは概略評価(スケッチプランニング)を目的とし、
> 国交省マニュアル準拠の需要予測(B/C 算定の正式値)を代替するものではない。
> この位置づけは UI 上にも明記する。

```
┌───────────────┴─────────────────────────────────┐
│ 計算エンジン (Python パッケージ、API から独立利用可) │
│  network:  グラフ構築・最短経路 (igraph/NetworkX)   │
│  demand:   需要予測 (重力モデル・機関分担・配分)      │
│  benefit:  時短効果・便益の集計                     │

                │
┌───────────────┴─────────────────────────────────┐
│ データ層                                          │
│  前処理済みデータ: GeoParquet / SQLite (同梱・DL)   │

│  地図タイル: 地理院タイル / OpenStreetMap            │
└─────────────────────────────────────────────────┘
```

### 設計方針

- **計算エンジンを API から分離**し、Jupyter やバッチからも使えるライブラリにする
  (テスト容易性・研究用途を考慮)
- 最初は **ローカル完結**(SQLite + ファイル)で動くようにし、
  サーバー運用(PostgreSQL + ジョブキュー)は後から差し替え可能な構成にする
- 計算は数十秒かかり得るため、**非同期ジョブ**(投入 → ポーリング → 結果取得)とする

### 技術スタック(案)

| 層 | 技術 | 選定理由 |
|---|---|---|
| フロント | React + TypeScript + Vite | 標準的で情報が多い |
| 地図 | MapLibre GL JS + 地理院タイル | 無料・日本の地図品質が高い |
| 大量描画 | deck.gl (ArcLayer, TripsLayer 等) | OD 流動・断面交通量の描画 |
| グラフ表示 | ECharts or Recharts | 集計結果のチャート |
| API | FastAPI + Pydantic | 型安全・OpenAPI 自動生成 |
| 計算 | numpy / pandas / GeoPandas / igraph(または NetworkX) / shapely | igraph は大規模グラフで高速 |
| データ格納 | GeoParquet(静的データ)+ SQLite(シナリオ) | セットアップ不要で始められる |

## 3. データ設計

### 3.1 利用する公開データ(日本国内)

| データ | 出典 | 用途 |
|---|---|---|
| 鉄道路線・駅 (N02) | 国土数値情報(国交省) | 既存鉄道ネットワークの構築 |
| 駅別乗降客数 (S12) | 国土数値情報 | 需要モデルのキャリブレーション |
| バス路線 (N07)・バス停 (P11) / GTFS-JP | 国土数値情報 / 各事業者 | バスネットワーク(拡張フェーズ) |
| 国勢調査 人口(4分の1地域メッシュ〜500m メッシュ) | e-Stat | 駅勢圏人口・トリップ発生量 |
| 経済センサス 従業者数メッシュ | e-Stat | トリップ集中量(就業地側) |
| 将来推計人口メッシュ | 国土数値情報 | 将来年次のシナリオ評価(拡張) |
| 大都市交通センサス / パーソントリップ調査 | 国交省・都市圏 | OD 分布・パラメータ検証(拡張) |

前処理パイプライン(`scripts/prepare_data/`)で上記を取得・正規化し、
GeoParquet に変換して配布(またはユーザーがスクリプトで生成)する。
**生データはリポジトリに含めず**、出典・ライセンス表記を明確にする。

### 3.2 内部データモデル

#### ネットワーク(既存網・前処理済み)

```
Station   : id, name, operator, lines[], geometry(Point), daily_boardings
Link      : id, from_station, to_station, line_id, length_m,
            travel_time_s, headway_s(運行間隔), mode(rail/bus), geometry(LineString)
Line      : id, name, operator, mode, links[]
TransferLink : from_station, to_station, walk_time_s   # 乗換・近接駅間徒歩
Zone      : id, geometry(500m メッシュ), population, employees
ZoneAccess: zone_id, station_id, access_time_s          # ゾーン⇔駅のアクセス(徒歩/フィーダー)
```

- 駅間所要時間は時刻表が無い区間もあるため、**距離 ÷ 表定速度(路線種別ごとの既定値)**で
  補完し、実時刻表(GTFS 等)があれば上書きする
- 待ち時間は頻度ベースで `headway / 2` を初乗り・乗換時に加算(RAPTOR 等の
  時刻表厳密探索は将来拡張とする)

#### シナリオ(ユーザー入力)

```
Scenario     : id, name, description, base_network_version, created_at
NewLine      : scenario_id, name, mode, avg_speed_kmh, headway_min, fare_rule
NewStation   : scenario_id, name, geometry(Point),
               transfer_to[]  # 既存駅との乗換(自動検出+手動調整)
NewLink      : scenario_id, from, to, geometry, travel_time_s(自動計算・手動上書き可)
```

#### 計算結果

```
RunResult    : scenario_id, run_id, params, created_at
StationVolume: run_id, station_id, boardings_per_day     # 駅別利用者数
LinkVolume   : run_id, link_id, passengers_per_day       # 区間断面交通量
ODChange     : run_id, origin_zone, dest_zone,
               time_before_s, time_after_s, trips
Summary      : run_id, new_line_daily_riders, total_time_saved_h_per_day,
               time_benefit_yen_per_year, population_within_isochrone, ...
```

## 4. 計算モデル設計

四段階推定法の簡易版をベースにする。段階的に精緻化できるよう、各ステップを
差し替え可能なインターフェースにする。

### 4.1 Step 0: ネットワーク構築

- 駅ノード + 路線リンク + 乗換リンク + ゾーン⇔駅アクセスリンクから有向グラフを構築
- エッジコスト = 乗車時間 + 待ち時間(headway/2)+ 乗換ペナルティ(既定 5 分、設定可)
- 新設路線はシナリオ適用時にグラフへ**オーバーレイ**(ベース網は不変・共有)
- 新駅⇔既存駅の乗換リンクは距離閾値(例: 徒歩 10 分圏)で自動生成し、UI で編集可能

### 4.2 Step 1: 発生・集中(Trip Generation)

- ゾーン(500m メッシュ)ごとに
  `発生量 = 人口 × 原単位`, `集中量 = 従業者数 × 原単位`
- 原単位は駅別乗降客数(S12)との整合でキャリブレーション(地域ブロック別に係数調整)

### 4.3 Step 2: 分布(Trip Distribution)— 重力モデル

```
T_ij = k · G_i · A_j · f(c_ij)      f(c_ij) = exp(−β·c_ij) など
```

- `c_ij` は公共交通の一般化費用(所要時間 + 運賃換算)
- フレーター法等で発生・集中制約を満たすよう収束計算

### 4.4 Step 3: 機関分担(Mode Choice)— 二項ロジット

```
P(公共交通) = 1 / (1 + exp(−(V_transit − V_car)))
V = −α·時間 − γ·費用 + 定数(地域タイプ別)
```

- 対自動車の転換を扱う。MVP では「公共交通トリップ固定+新線への転換のみ」とし、
  誘発需要・自動車からの転換はフェーズ 3 で導入
- パラメータ既定値は既往研究・交通センサスから設定し、設定画面で変更可能にする

### 4.5 Step 4: 配分(Assignment)

- 頻度ベースの最短経路(Dijkstra)による全量配分を基本とする
- 同等コスト経路への分散が必要な場合はロジット配分(経路選択確率 ∝ exp(−θ·cost))
- 出力: 駅別乗降・区間別断面交通量・新線の日利用者数

### 4.6 効果指標の算定

| 指標 | 算定方法 |
|---|---|
| 新線利用者数(人/日) | 配分結果の新線リンク通過量 |
| 駅別乗降人員 | 配分結果の駅別集計(整備前後差分も) |
| 所要時間短縮 | 整備前後の OD 所要時間行列の差 × トリップ数 → 総時短(人・時間/日) |
| 時間便益(円/年) | 総時短 × 時間価値原単位(既定 約 40 円/分、設定可)× 年間換算 |
| アクセシビリティ | 任意地点からの等時圏(30/60 分)人口・従業者数の前後比較 |
| 既存路線への影響 | 並行路線の断面交通量の増減 |

**「整備前」「整備後」の 2 ケースを同一パラメータで計算し差分を取る**ことを全指標で徹底する。

## 5. API 設計(概要)

```
GET  /api/network/stations?bbox=...        既存駅(地図表示用、ベクトルタイル化も検討)
GET  /api/network/lines?bbox=...           既存路線

POST /api/scenarios                        シナリオ作成
GET  /api/scenarios/{id}                   取得(新線・新駅・新リンク含む)
PUT  /api/scenarios/{id}                   更新(路線編集の保存)
POST /api/scenarios/{id}/duplicate         複製(A案→B案)

POST /api/scenarios/{id}/runs              計算ジョブ投入(モデルパラメータを body で)
GET  /api/runs/{run_id}                    状態 (queued/running/done/failed) + 進捗
GET  /api/runs/{run_id}/summary            サマリー指標
GET  /api/runs/{run_id}/link-volumes       断面交通量 (GeoJSON)
GET  /api/runs/{run_id}/station-volumes    駅別利用者数 (GeoJSON)
GET  /api/runs/{run_id}/isochrone?origin=&minutes=&case=before|after
GET  /api/runs/{run_id}/od-changes?min_saving=  時短の大きい OD ペア (GeoJSON Arc用)

POST /api/compare?runs=r1,r2               複数シナリオ比較用サマリー
```

## 6. フロントエンド設計

### 6.1 画面構成

```
┌────────────┬──────────────────────────────┬────────────┐
│ シナリオ    │                              │ 結果パネル   │
│ 一覧/切替   │        地図 (MapLibre)        │ ・サマリー   │
│            │   既存網 / 新線編集 / 結果表示   │ ・チャート   │
│ 路線編集    │                              │ ・レイヤー   │
│ パネル      │                              │   切替      │
└────────────┴──────────────────────────────┴────────────┘
```

### 6.2 路線編集 UI(コア体験)

1. 「新規路線」→ 地図クリックで駅を順に置く(スナップ: 既存駅に近いと乗換候補を提示)
2. 駅間は自動で直線 or 中間点ドラッグで線形調整。距離と表定速度から所要時間を自動計算
3. サイドパネルで路線属性(種別・表定速度・運行間隔・運賃)と駅ごとの属性を編集
4. 「計算実行」→ 進捗表示 → 結果レイヤーが地図に重なる

### 6.3 可視化レイヤー

| レイヤー | 表現 |
|---|---|
| 断面交通量 | リンクの**線の太さ+色**(整備後)/ 前後差分は青(増)赤(減)の発散配色 |
| 駅別乗降 | 駅の円サイズ |
| 等時圏比較 | 整備前後の等時圏ポリゴンを重ね、拡大部分を強調 |
| 時短ヒートマップ | メッシュ別の到達時間短縮量をコロプレス表示 |
| OD 流動 | deck.gl ArcLayer(時短上位 OD ペア) |
| シナリオ比較 | 2 案並列(スワイプ or 左右分割)+ 指標の比較表 |

## 8. 開発フェーズ計画

### Phase 1: ネットワーク & 時短効果(MVP)

- 国土数値情報から鉄道ネットワーク構築(1 都市圏、例: 首都圏 or 任意県からスタート)
- 地図表示・新設路線の入力 UI・シナリオ保存
- 最短経路・等時圏の整備前後比較、**メッシュ人口ベースのアクセシビリティ指標**
- → この時点で「時短効果の可視化」まで動く

### Phase 2: 需要予測

- メッシュ人口・従業者数の統合、発生集中 → 重力モデル → 全量配分
- 駅別乗降(S12)によるキャリブレーションと精度レポート
- 新線利用者数・断面交通量・駅別乗降の可視化、時間便益の概算

### Phase 3: 精緻化・比較機能

- 機関分担(対自動車)・誘発需要、運賃の一般化費用への反映
- シナリオ並列比較 UI、結果のレポート出力(PDF/CSV)
- バスネットワーク(GTFS-JP)の統合、全国データ対応

## 9. 検証方針

- **ユニットテスト**: 小さな人工ネットワーク(数駅)で最短経路・配分・便益計算の期待値を固定
- **再現性テスト**: 既存路線のみで配分した結果と S12 駅別乗降の相関(R² 等)を CI で監視
- **感度分析**: β・乗換ペナルティ等の主要パラメータを振って結果の安定性を確認
- **ベンチマーク**: 実在の近年開業路線(例: 相鉄・東急直通線など)で事前予測と実績の
  オーダー比較を行い、精度の目安をドキュメント化

## 10. 主要な設計上の論点(要検討)

1. **対象範囲の初期値**: 全国一括はデータ量・計算量が大きい。MVP は 1 都市圏に限定し、
   対象エリアを選択して読み込む方式を推奨
2. **時刻表ベース探索(RAPTOR)の要否**: 概略評価では頻度ベースで十分。
   ダイヤ依存の分析が必要になった段階で導入
3. **自動車側ネットワーク**: 機関分担に対自動車の所要時間が必要。
   MVP では直線距離 × 平均速度の近似で開始し、道路ネットワーク(OSM)は後日
4. **配布形態**: ローカルアプリ(Docker Compose 一発起動)を基本とし、
   Web サービス化は需要を見て判断
